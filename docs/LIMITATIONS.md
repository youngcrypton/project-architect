# Project Architect — Known Limitations & Boundaries

This document defines the operational boundaries, known platform limitations, and design trade-offs of the Project Architect system.

---

## 1. Scope & Role Boundaries

- **Not an Autonomous Coding Agent**:
  - Project Architect's primary mission is context management, task planning, memory maintenance, and verification. It is intentionally designed NOT to autonomously write application code or replace coding agents like Claude Code or Cursor.
  - Changes to application source code must be performed by the developer's chosen coding agent using the prompts generated by `pa-task-prompt`.

- **Read-Only Auditing**:
  - During `pa-project-audit`, the agent strictly enforces read-only access to product files. It will not apply automated "quick-fixes" to code defects discovered during an audit.

- **Non-Destructive Operations**:
  - Project Architect will never run destructive git operations (e.g. `git reset --hard`, `git push --force`), delete user codebases, or push commits to remote repositories without explicit user instruction.

---

## 2. Storage & Memory Scale

- **Local Markdown Files**:
  - Memory is intentionally stored as plain Markdown files in `<project-root>/.project-architect/` to ensure privacy, portability, and zero-cost hosting.
  - *Limitation*: For exceptionally large enterprise repositories (hundreds of thousands of lines across dozens of microservices), traversing all Markdown files simultaneously may consume significant context tokens.
  - *Mitigation*: Progressive disclosure is used — agents read specific memory files relevant to the active task (e.g. `REQUIREMENTS.md` and `TASKS.md`) rather than reading the entire directory at once.

- **No Vector Database or External Service**:
  - To respect privacy and eliminate paid API dependencies, semantic search and vector stores are omitted in the MVP. All memory queries rely on structured directory traversal and cross-references.

---

## 3. Platform & Agent Environment

- **Declarative Agent Definitions in Plugins**:
  - Antigravity plugins currently support Skills, Rules, Hooks, and MCP servers, but do not provide a declarative manifest for persistent subagents.
  - *Resolution*: Specialist roles (Product Analyst, Prompt Engineer, Memory Manager, Code Auditor) are implemented as specialized skills (`pa-discovery`, `pa-task-prompt`, `pa-memory-update`, `pa-project-audit`). Antigravity's dynamic subagent invocation (`invoke_subagent`) remains available at runtime if needed.

- **Rules Aggregate Context Budget**:
  - Antigravity enforces an aggregate rules budget of 20,000 tokens across all active rules. The `rules/AGENTS.md` file is kept compact (~2.4 KB / ~600 tokens) to minimize context consumption.

---

## 4. Privacy & Secrets

- **No Credential Storage**:
  - Project Architect explicitly refuses to store passwords, API keys, tokens, or private secrets in project memory files. Any credentials provided in prompts or logs are intercepted and sanitized.
