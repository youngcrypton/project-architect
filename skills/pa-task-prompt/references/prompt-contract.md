# Implementation Prompt Contract & Template Guide

This document defines the strict specification for prompts generated by Project Architect's `pa-task-prompt` skill. Every generated implementation prompt must adhere to this contract to ensure coding agents receive complete, unambiguous, and hallucination-free instructions.

---

## 1. Prompt Generation Principles

1. **Reality First (Zero Hallucination)**:
   - Never invent directory structures, file paths, function signatures, package versions, or API endpoints.
   - If files exist, reference real paths verified through file inspection.
   - If no codebase exists, explicitly state: `Existing Codebase: None (Greenfield project - start from foundation)`.

2. **Self-Contained & Copy-Ready**:
   - The coding agent executing the prompt may have zero prior conversation history.
   - All necessary business logic, acceptance criteria, constraints, and context must be explicitly included.

3. **Strict Scope Boundaries**:
   - Explicitly define both what is **In Scope** and what is **Out of Scope (Non-Goals)** to prevent coding agent drift.

4. **Actionable Verification & Reporting**:
   - Require the coding agent to run tests, perform type checks, and report all modified files and residual risks.

5. **Zero AI Fingerprints & Human Engineering Rigor**:
   - Prompts must explicitly prohibit the coding agent from outputting AI tells, robotic commentary, assistant pleasantries, redundant comments, or incomplete stubs.
   - The resulting code and git artifacts must appear completely human-crafted by a principal engineer.

---

## 2. Standard Prompt Template

When generating an implementation prompt, output it in the following structure:

````markdown
# TASK: [TASK-ID] - [Task Title]

## 1. Objective & Role
- **Role**: Senior Software Engineer / Full-Stack Developer
- **Objective**: [1-2 sentences on exactly what needs to be implemented and the expected outcome]
- **Milestone / Tracking**: Milestone [MS-XXX], Requirement(s) [REQ-XXX]

## 2. Product Context & User Story
- **Context**: [Brief context explaining why this feature is being built and how it fits into the broader system]
- **User Workflow**: As a [User Persona], when I [Trigger / Action], I want to [Behavior / Process] so that [Outcome / Value].

## 3. Current Codebase State & Relevant Files
- **Codebase Status**: [No codebase / Existing repository]
- **Key Files & Symbols**:
  - `path/to/file1.ext`: [Role of this file and relevant functions/types]
  - `path/to/file2.ext`: [Role of this file and relevant functions/types]
- **Existing Conventions**: [Identified patterns, naming conventions, state management patterns, styling approaches]

> *(Note: If no codebase exists, clearly specify recommended initialization commands or starter scaffolding according to project decisions).*

## 4. Scope & Non-Goals
### In Scope
- [Concrete deliverable 1]
- [Concrete deliverable 2]
- [Concrete deliverable 3]

### Out of Scope (Non-Goals)
- [Explicitly excluded item 1]
- [Explicitly excluded item 2 - defer to future tasks]

## 5. Technical Constraints & Decisions
- **Stack / Dependencies**: [Verified frameworks, libraries, versions, e.g. React 19, TypeScript, Tailwind]
- **Architecture & Patterns**: [Specific architecture pattern, e.g., service layer, server action, repository pattern]
- **Data Model / Contracts**: [Exact schema, interface signatures, or API contract expectations]

## 6. Detailed Implementation Requirements & Edge Cases
- **Happy Path Behavior**: [Step-by-step description of expected runtime behavior]
- **Edge Cases & Failure Handling**:
  - [Edge case 1: e.g. Network error / Offline state] -> [Expected fallback or error message]
  - [Edge case 2: e.g. Empty list / Zero state] -> [Expected UI display]
  - [Edge case 3: e.g. Validation failure / Malformed input] -> [Validation response]
- **Security & Privacy**: [Input sanitization, authentication check, secret management]
- **Accessibility & Responsiveness** (if UI): [Keyboard navigation, ARIA attributes, mobile/desktop layout]

## 7. Anti-AI Fingerprint & Craftsmanship Contract
- **No AI Clichés or Marketing Fluff**: Strictly ban buzzwords (*delve, tapestry, seamless, leverage, revolutionize, cutting-edge, game-changer, supercharge*) from code, UI copy, comments, and commit messages.
- **No Redundant Comments**: Do NOT write comments that narrate the obvious syntax (e.g. `// return user`, `// set state to true`, `// handle error`). Write comments ONLY for non-obvious business logic, browser quirks, or complex algorithmic trade-offs.
- **No Placeholder Stubs**: Zero `// TODO: implement later` or empty mock functions. Every path, error handler, and edge case must be fully implemented.
- **No Assistant Meta-Attribution**: Do NOT include conversational filler (*"Certainly!", "Here is the code"*), assistant disclaimers, or synthetic co-authorship tags (*"Co-authored-by: AI"*, *"Generated by AI"*). Commit messages and PR descriptions must use standard conventional commits written like a human senior engineer.

## 8. Testing & Verification Instructions
- **Unit / Integration Tests**: [Specific test cases to write or update, expected test runner command]
- **Manual Verification Steps**:
  1. [Step 1: Setup or start server]
  2. [Step 2: Trigger action]
  3. [Step 3: Verify observable result]

## 9. Acceptance Criteria Checklist
- [ ] [Criterion 1]
- [ ] [Criterion 2]
- [ ] [Criterion 3]
- [ ] [Code compiles with zero type errors / lint warnings]
- [ ] [Tests pass successfully]
- [ ] [Free of AI boilerplate, redundant comments, and placeholder stubs]

## 10. Coding Agent Reporting Requirements
Upon completion, provide a concise summary containing:
1. **Changed Files**: List of all created, modified, or deleted files.
2. **Commands & Tests Run**: Exact verification commands executed and pass/fail outputs.
3. **Known Limitations & Remaining Risks**: Any assumptions made, deferred tasks, or areas needing review.
````

---

## 3. Verification Rubric

Before presenting the prompt to the user, ensure:
1. Does it reference any non-existent files as existing? (If yes, fix or remove).
2. Are the acceptance criteria testable and binary (pass/fail)?
3. Are non-goals clearly stated to prevent rabbit-holes?
4. Are security, error handling, and edge cases addressed?
5. Is the prompt copy-ready without requiring additional explanation?
6. Does it enforce the Anti-AI Fingerprint & Craftsmanship Contract?
